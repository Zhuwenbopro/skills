# Bug 经验撰写

## 目标

将已经完成的 Bug 调查报告压缩为经验库知识，而不是复制调查过程。经验条目只记录经过当前案例证据支持、并且可能跨案例复用的结论和处理方法。

## 调用前提

只有同时满足以下条件才能调用本 skill：

1. 原始失败已经真实复现，或报告明确记录了无法复现且用户只要求整理已证实事实；
2. 根因状态为 `已证实`，有错误原文、运行日志或源码机制证据；
3. 修复已经真实验证，至少有失败到成功的可比较结果；
4. 若存在混杂变量，报告已明确标记，不能把混杂实验写成单变量结论；
5. 经验内容不包含机密、模型权重、临时 PID、端口、时间戳或仅适用于单次环境的细节。

如果根因、修复或关键验证仍为 `待验证`、`受阻` 或“最可能原因”，不要写入经验库；应保留在案例报告中。

## 输入

- 已完成的 Bug 调查报告；
- 现有 `references/experience-index.md`；
- 目标经验条目，或根据症状选择现有条目；
- 必要时读取报告引用的关键 artifact，核对决定性证据。

## 撰写标准

经验条目优先使用以下结构，保持短小：

```markdown
# <症状/问题> 经验

## 适用范围

<哪些错误现象适用；不要扩大到未验证的故障类型。>

## 已验证原因和解决方法

| 已验证原因 | 证据表现 | 已验证解决方法 |
|---|---|---|
| ... | ... | ... |

## 已验证处理方式

1. ...
2. ...

## 结论边界

- ...
```

必须遵守：

- 标题描述症状或问题，不把单次案例当成通用根因；
- 只写报告中标记为 `已证实`、`已排除` 或由决定性 artifact 直接支持的内容；
- 每个“解决方法”都要能追溯到真实验证结果；
- 把错误原文或稳定关键词保留下来，便于后续检索；
- 用“已验证原因”“已验证解决方法”，不要写“常见原因”“可能原因”；
- 不把未测试的候选项、经验猜测、源码推测写进表格；
- 删除过程性细节：实验编号、长日志、完整命令、GPU/端口/PID、时间线和失败假设表；
- 若报告只验证了一个原因，就只写一个原因；不要为了完整而补充其他类别；
- 若现有条目已覆盖同一故障，修改并合并，不新建重复条目；
- 若报告证据不足以形成可复用知识，不修改经验库，并说明原因。

## 更新索引

新增或重命名条目时同步更新 `references/experience-index.md`：

- 症状关键词必须能帮助后续匹配；
- 用一句话说明条目用途；
- 相近条目合并，避免索引膨胀；
- 索引规则明确写出：经验不能替代当前案例复现，当前证据优先。

## 完成检查

写入前逐项检查：

- [ ] 根因确实为 `已证实`；
- [ ] 修复有真实成功证据；
- [ ] 没有把混杂实验写成单变量结论；
- [ ] 每条经验都能回溯到报告或 artifact；
- [ ] 没有未经验证的“常见原因”；
- [ ] 条目简洁，没有单次环境细节；
- [ ] 索引已同步；
- [ ] 文件格式检查通过。
