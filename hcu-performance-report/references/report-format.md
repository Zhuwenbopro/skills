# 报告版式与发布

本文件配合 [可交付报告契约](report-contract.md) 使用。契约规定是否可交付；本文件规定正文如何排版。

正文只保留简短标题、核心表格和图片。默认单个节点、单组有效配置一篇报告；跨节点比较只在用户明确需要时增加，不自动附历史章节。

## 固定结构

1. 标题：模型 + 节点 + 运行环境与性能。
2. 运行环境与有效配置：一张表。
3. 硬件实测参考：一张表。
4. 测试方法：一张表。
5. DRAFT / VERIFY 类别双饼图：一张图。
6. DRAFT 调用顺序：一张折叠算子表。
7. VERIFY 调用顺序：一张折叠算子表。

典型双阶段报告共 5 张表、1 张图，另有服务器审计 JSON。若已有资料确实只有一个阶段，仅呈现实际阶段，并在方法表简短注明覆盖范围。不得为满足版式虚构数据。

### 运行环境与有效配置

用“项目｜有效值”两列，必要时加极短备注。覆盖足以解释本次数据的项目：

- 节点、卡型号与数量、实际卡号、模型和 dtype、TP。
- SGLang、adapter / plugin、PyTorch / DTK 等实际版本或提交。
- 本次捕获生效的 MTP 算法与关键参数、Graph 开关和范围、流设置及相关环境变量。

按实际资料精简合并行，避免把启动命令或 JSON 整段贴进正文。原始配置保存在服务器。未知值用“—”，不要把当前默认配置写成捕获时的事实。

### 硬件实测参考

建议列“项目｜参考结果｜测量规模/口径”。包括已有的 HBM、P2P 单向/双向、BF16/INT8 GEMM，按现有数据取舍。统一单位，保留矩阵规模、方向等影响对比的条件。

同方法、同单位且接近的卡合成一份代表值，逐卡原始结果不进入正文。差异实质影响判断时，才分列有区别的结果；不为排版而掩盖差异。

### 测试方法

用“项目｜实际设置”两列，写明：

- 实际输入 token、实际输出 token及适用时的最大输出限制。
- 请求数、并发、采样参数。
- 预热、缓存命中或清理情况。
- 捕获阶段和窗口、选取的 rank / replay 数。
- 耗时与次数的汇总单位。DRAFT / VERIFY 正文默认报告每个 decode 周期或 replay 的平均 GPU kernel 时间；“次数已含折叠重复”仍需保留，原始多次合计放在服务器审计数据中，除非用户明确要求累计量。阶段跨度、scheduler annotation 和周期起始间隔须单独标明。
- Graph 报告须注明 DRAFT/VERIFY 使用的是 `gpu_user_annotation` 还是 `user_annotation`。Perfetto 选区里的 annotation wall duration、kernel self duration 和去重后的 GPU kernel duration 分别列示；父子 GPU scope 不得重复计时。

用户举的“4K 输入 / 1K 输出”不是已测事实。已有数据若是 1024 / 32 就写真实长度，其他测试同理。不为缺失信息写推断性的默认值。

### DRAFT / VERIFY 双饼图

- 优先沿用已确认的双图样式：同一图中并排两个阶段，通信、GEMM、逐元素、其他四类，类别颜色在两图之间一致。
- 类别名和占比直接标注；小扇区用清晰引线，文字不得重叠或裁切，中文字体可读。
- 百分比与同份发布数据一致。没有时间的类别不画虚构扇区；低占比不能为美观挪到其他类。
- 图中可用简短阶段标题标明相应统计的每周期平均时间及单位；若图展示累计量，标题必须明确写“累计”。不要添加重复的“类别占比与总体时间”表。
- 沿用已有图片前先确认其数据范围和口径一致；需要更新时在服务器绘图。检查最终图片，不只检查绘图脚本是否成功。

### 调用顺序表

DRAFT、VERIFY 各一张表，固定使用这些字段：

| 顺序 | 模块/函数 | 归属类别 | 简短作用 | 输入/权重/输出 shape | 次数/replay（单 step） | 总耗时 | 单次耗时 | 算力利用率 | 带宽利用率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- 真实模型模块/函数名保持可辨识；作用用短语，不写长段讲解。
- 参考交付通常包含几十行级别的折叠调用链，而不是只有阶段 annotation 的 3–4 行摘要。若只能生成摘要，必须把它标为中间分析结果，不能作为最终报告。
- 调用链不足以支持完整映射时，正文仍可保留粗行，但必须同时在 `source-map.json` 和 `coverage.json` 标出未映射或未证明项，并将报告状态设为 `incomplete`。
- 按实际调用顺序排列所有函数，不按类型分表、不按耗时排名。
- “归属类别”从发布数据读取，与饼图统一为 `GEMM`、`Element-wise`、`Other`；存在通信时再显示 `Communication`。分类不能只留在图中。
- 重复片段折叠并注明层范围、重复次数及嵌套结构；内外部顺序都要保持。分组行可标记重复体，数据行中的次数已含外层重复。
- shape 采用紧凑的输入、权重、输出记法；无权重或信息缺失用“—”，不能补猜。动态形状用真实范围或保留必要变体。
- 时间单元格带单位，或在表头统一标明。总耗时与单次耗时服从方法表中的范围。
- 利用率保留适度小数；无可靠分母或不适用时用“—”。
- 参数量、FLOPs 不进正文。不要为它们增加列。

对于 W4A8 / W4 模型，运行环境表必须同时写权重格式、激活/计算路径和硬件参考的限制；调用顺序表中的带宽利用率只填有真实逻辑字节分子和可信 HBM/流式分母的算子，其余保持“—”。

## 正文排除项

不添加“模块映射与计算口径”“主要时间分布”“复核产物”，不添加饼图后的类别占比/总体时间重复表，不追加原始路径和审计日志，不按算子类型重建分表。

映射、公式、字节、FLOPs 和完整校验保存在服务器。若有影响理解的缺项，将一句最短说明放入相关表格；不要追加长篇方法论。

## 文档写入与回读

1. 确认目标文档和编辑范围。整篇替换必须来自用户明确的重写指令；普通“更新报告”采用相应位置的更新。已有范围授权不重复询问。
2. 读取当前内容及版本，在服务器备份原文，保存待发内容和其使用的数据来源。修改前完成分析、表格和图片校验。
3. 飞书用 lark-doc skill / 当前已认证工具操作，不把 API 密钥、浏览器凭据或其他容器的认证复制进脚本。本地客户端确有必要时，只在内存中桥接发布内容，服务器脚本及原始 trace 仍留在服务器。
4. 可用版本守卫时带上刚读到的 revision；版本冲突先读取差异，不能无条件覆盖协作修改。
5. 写入后回读，核对标题、表数、表头、单元格、图片及统计范围；确认旧节点和删除章节没有残留。将读回结果与服务器待发内容比较，保留结论。
6. 图片导入可能重新编码并分配新 token，不能要求新旧 token 一致。检查图片绑定、尺寸和可见内容；工具支持时用原生预览验证，不为预览回传服务器脚本。
7. 简短返回文档链接、完成状态和真正缺项。失败或部分写入如实报告，不将待发稿当作已发布。
