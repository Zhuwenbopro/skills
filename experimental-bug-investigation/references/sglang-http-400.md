# SGLang HTTP 400 经验

## 记录失败原因

至少保留：

- 请求方法和 URL；
- 客户端实际发送的 JSON；
- HTTP 状态码和完整响应体；
- 服务端同一时间段的错误日志；
- 启动命令中的模型、上下文长度、量化、speculative 和后端参数。

优先看响应体。SGLang 通常会直接说明是字段、模板、token 数量或采样参数不合法。

## 已验证原因和解决方法

| 已验证失败原因 | 证据表现 | 已验证解决方法 |
|---|---|---|
| 请求的输出 token 预算超过服务有效上下文长度 | SGLang 返回 `max_completion_tokens is too large`，并明确给出请求值和允许上限 | 检查服务最终生效的 `context_length`，将 `max_tokens` / `max_completion_tokens` 降到上限以内；若确实需要更长输出，再显式调整服务上下文长度 |

## 已验证处理方式

1. 保存完整响应体，不要只记录 400。
2. 对照服务启动日志确认 `ServerArgs.context_length` 和最终 `context_len`，不要只根据模型配置或启动脚本推测。
3. 只修改请求输出预算进行验证；如果同时修改了服务启动参数，必须把结果标为混杂实验。
4. 对评测工具按数据集设置合理的 `max_tokens`，避免用一个过大的全局默认值覆盖短代码生成任务。

## 结论边界

- 服务启动参数错误通常导致服务启动失败，不应与服务已启动后的 HTTP 400 混为一谈。
- “降低 `max_tokens` 后成功”只有在服务启动参数不变时，才能作为长度配置的单变量验证；若同时改变了服务的 `context_length`，必须明确记录混杂因素。
- 本条目只记录已验证的长度配置问题；其他 400 类型在实际验证前不写入经验库。
