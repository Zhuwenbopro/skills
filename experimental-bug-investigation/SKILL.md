# 实验驱动的 Bug 调查

## 目标

把用户案例转化为可重复、可证伪的调查。最终结论必须由真实实验支持，而不是只靠读代码或经验推断。

调查全程维护一份 Markdown 报告。报告是事实账本，不是思考草稿：简洁、可扫描、可复跑。

## 不可违反的规则

1. **先记录，后实验**：收到案例后立即创建报告，原样保留关键命令、请求和期望/实际行为。
2. **先复现，后定因**：未成功复现时，不得把假设写成根因。
3. **证据分级**：每条结论标记为 `已证实`、`已排除`、`待验证` 或 `受阻`。
4. **一次只改一个变量**：对照实验尽量保持单变量；无法做到时明确记录混杂因素。
5. **保留错误原文**：HTTP 状态码不足以定位问题；必须保存响应体、关键日志、退出码和必要的栈信息。
6. **真实验证**：代码阅读、搜索结果和推理只能生成假设；根因与修复需要执行命令、测试、请求或最小程序验证。
7. **禁止伪造成功**：不能运行的实验写 `受阻` 并说明缺少的条件，不得写“应当通过”。
8. **保护现场**：先检查已有进程、端口、GPU/内存、工作树和用户修改。不得覆盖用户日志或清理非本次进程。
9. **修复须双重验证**：既验证失败案例由 fail 变 pass，也运行邻近回归测试；必要时验证反例仍然失败。
10. **控制报告篇幅**：正文只保留决定性证据；长日志写入独立 artifact，报告引用路径和关键摘录。
11. **缺失触发器不等于停止实验**：如果案例只有部分可执行，仍须原样执行已有前置步骤、验证其完成条件，并运行不冒充原 workload 的最小探测；只把完整症状复现标为受阻。
12. **结束必须释放资源**：无论成功、失败或受阻，结束前停止本次启动的服务和子进程，释放端口、GPU/CPU/共享内存及锁，并删除不需保留的临时敏感文件。不能只发送信号；必须复查资源确已释放。

## 报告位置和命名

默认在仓库根目录创建：

`bug-reports/YYYYMMDD-HHMM-<short-slug>.md`

配套产物放在同名目录：

`bug-reports/YYYYMMDD-HHMM-<short-slug>/`

如果用户指定路径，服从用户。不要把模型权重、大型 core dump 或敏感请求复制进仓库；仅记录其安全路径、摘要和校验信息。

使用 [报告模板](./references/report-template.md)。创建后每完成一个阶段就更新，不要等调查结束再补写。

## 工作流

### 0. 建立案例记录

先记录：

- 用户原始现象与期望行为；
- 启动命令、环境变量、请求命令或测试命令；
- 时间、仓库提交、工作树状态、平台和相关依赖版本；
- 已知限制与敏感信息脱敏说明。

为案例定义一个**可机器判定的失败谓词**，例如：

- `HTTP 状态码属于预期失败集合`；
- 进程退出码非 0 且日志包含固定错误；
- 输出与基准误差超过阈值；
- 在截止时间内未完成。

若案例缺失真正触发异常的动作（例如只有系统初始化步骤，却没有业务 workload），立即记录“复现输入不完整”。先主动收集本机证据；只有无法从日志、历史或运行中恢复时，才向用户索要**最小缺失项**。

此时不得因为“无法完整复现”而跳过已有命令。应把实验拆成两个独立结论：

- **可执行前置路径**：原样执行已有步骤，验证初始化、健康状态、运行信息和最小合法 workload；
- **用户症状路径**：只有确切触发器才能判定是否复现用户报告的症状。

最小请求成功只能证明基础路径可用，不能证明用户报告不存在。

### 1. 保护性环境盘点

在执行案例前检查：

- `git status` 和当前提交；
- 命令、模型、数据、配置文件是否存在；
- 端口和同类服务是否已占用；
- GPU/CPU/内存/磁盘可用量；
- 当前相关进程；
- 凭据和外部依赖是否就绪。

将结果压缩为 3–8 行写入报告。长清单存 artifact。

对于 GPU 服务，不得仅凭利用率为 0 判断设备空闲；同时检查显存和进程占用。

### 2. 原样复现

优先运行用户给出的原始命令，不先“修正”它。

- 服务进程写入唯一日志文件并记录 PID；
- 等待明确的 readiness/health 条件，而不是固定睡眠；
- 执行**确切的触发请求或 workload**；
- 捕获 stdout、stderr、退出码、响应头/体及时间；
- 至少重复一次以区分稳定失败和偶现失败；偶现问题记录成功率和样本数。

复现成功后，在报告摘要中立即写一句：

> `已复现`：在 `<环境>` 执行 `<触发器>`，`<n>/<n>` 次命中失败谓词 `<谓词>`。

若只证明前置步骤成功，不等于复现了后续错误响应、错误输出或性能问题。

### 3. 建立假设全集

在动代码前写假设表。覆盖但不限于：

- 输入、schema、协议和客户端序列化；
- 配置、环境变量、默认值和参数组合；
- 模型/数据/artifact 的版本与完整性；
- 资源容量、并发、时序和竞态；
- 单机/多卡通信、拓扑和进程状态；
- 最近代码变更、依赖或 ABI 不匹配；
- 模板、解析器、token 长度、采样约束；
- 缓存、持久状态、端口或旧进程污染；
- 硬件/驱动/内核实现差异。

每项必须包含：`ID`、可能性、依据、反证、最小实验、状态。排序依据是：信息增益高、成本低、破坏性小优先。

“全部可能性”指覆盖合理故障类别，而非罗列无法验证的无限猜测。合并同源假设，避免同义重复。

### 4. 实验式收敛

为每个实验预注册：

- 要区分的假设；
- 唯一主要变量；
- 命令或步骤；
- 预期判据；
- 实际结果；
- 对假设状态的影响。

推荐顺序：

1. 无副作用的观测：响应体、日志、配置、版本、源码路径；
2. 最小输入；
3. 原请求字段二分；
4. 单参数 A/B；
5. 小模型、单卡或 CPU 最小复现；
6. 版本/提交二分；
7. 插桩、调试器、性能分析器。

负结果同样写入报告，因为它能排除假设。不要连续运行不能改变任何假设状态的实验。

### 4.1 按需使用经验库

完成当前案例记录和初始证据收集后，可查阅 [调查经验索引](./references/experience-index.md)。只加载与当前症状匹配的条目。

- 经验条目用于补充候选假设、最少证据和低成本实验，不替代当前案例复现；
- 不因历史案例相似就复制其根因或修复；
- 当前实验结果优先于经验；
- 案例特有命令、模型、端口和结论只写入案例报告，不回填主 Skill；
- 只有跨案例稳定复用的知识才进入经验库。

### 5. 使用子智能体隔离上下文

可将以下任务交给子智能体：

- 搜索所有错误产生路径；
- 分析长日志或栈；
- 独立构造最小复现；
- 运行一个互不干扰的实验矩阵；
- 审核根因链条是否有证据断点；
- 查找现有测试和回归覆盖。

给子智能体完整的工作目录、只读/可写边界、假设 ID、精确命令、判据、artifact 路径和返回格式。要求它只返回：命令、退出码、关键输出、结论、限制。主智能体必须核查决定性 artifact；不能仅凭子智能体意见宣布根因。

GPU、端口或同一工作树有共享冲突时，不并行运行实验。静态搜索和互不依赖的只读分析可以并行。

### 6. 构造根因链

只有同时满足以下条件，才能标记 `根因已证实`：

1. 原始失败可重复；
2. 有源码、配置或运行证据解释失败机制；
3. 关闭/改变单一原因后失败消失；
4. 恢复该原因后失败再次出现，或有等价的强反证实验；
5. 替代假设已被关键实验排除。

根因用最短因果链表达：

`触发输入/条件 → 出错分支 → 错误状态 → 用户可见症状`

如果只能满足部分条件，写“最可能原因”，并列出缺失实验。

### 7. 设计并实施修复

先在报告写候选方案及取舍：

- 修复层次是否正确（调用方、校验层、核心实现或文档）；
- 是否保持 API 兼容；
- 是否 fail-fast 并给出可操作错误；
- 对正确路径的影响；
- 风险和回滚方式。

优先最小、直接、可测试的修改。除非用户只要求调查，否则在根因明确后实施修复。

### 8. 验证修复

至少执行：

- **原始案例**：同命令、同请求、同失败谓词；
- **最小复现**：确认直接触发器被修复；
- **反例/边界**：确认无效输入仍得到正确错误；
- **邻近回归测试**：相关单测、集成测试或 lint/type check；
- **重复性**：对偶现问题提供样本数和结果。

报告必须展示修改前后的可比较结果。若只能做替代验证，明确说明与真实环境的差异。

### 9. 结束条件

结束前先执行清理：

1. 只定位并停止本次实验记录的 PID/进程组，不使用可能误杀用户任务的宽泛命令；
2. 优先正常终止，失败后再升级信号，并记录升级原因；
3. 核验监听端口已释放；
4. 核验子进程、worker、watcher 和后台终端已退出；
5. GPU 实验核验目标设备显存恢复到实验前基线；
6. 释放锁、共享内存和临时服务；保留报告所引用的非敏感 artifacts；
7. 把清理命令和核验结果写入报告。

若进程已成为 zombie，确认其不再持有端口、GPU、文件描述符或计算资源，记录其父进程和等待系统回收的事实；不要为清除 PID 表项重启或终止不属于实验的父进程。

然后更新报告所有章节，并给出：

- 根因状态；
- 最短证据链；
- 修改内容或建议；
- 验证命令与结果；
- 未解决风险；
- artifact 路径。

若根因与修复均已验证，调用 `bug-experience-writing` skill，将本次报告中经过证据支持且可跨案例复用的内容提炼到经验库。该调用不是必然新增条目：若内容仅适用于单次环境、存在未解决的混杂变量，或没有形成可复用结论，则不更新经验库。

停止条件只有四种：

- 根因与修复均已验证；
- 根因已验证，用户要求只调查不修改；
- 被明确外部条件阻塞，已列出解除阻塞所需的最小信息；
- 达到用户指定的时间/资源边界。

## 与已有技能协作

本技能负责通用“记录—复现—假设—实验—根因—修复—验证”闭环。问题边界清楚后，可切换到仓库已有专项技能，例如：

- 线上服务与 replay：`sglang-prod-incident-triage`；
- GPU 崩溃：`debug-cuda-crash`；
- 分布式卡死：`debug-distributed-hang`；
- 已知 good/bad 提交：`sglang-bisect-ci-regression`。

切换专项技能时继续维护同一份报告，不要另起互相矛盾的事实账本。

Bug 已成功解决且完成真实验证后，使用 `bug-experience-writing` 将可复用结论整理到经验库；未经验证的猜测只保留在案例报告中。
